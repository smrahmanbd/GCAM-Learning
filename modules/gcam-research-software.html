Research brief

In this module you will

  • Trace a GCAM run from gcamdata and input XML through the solver to the output database and queries
  • Explain why GCAM solves for market-clearing prices period by period rather than optimising over time
  • Say what share-weights do in calibration and why they are not free parameters

Spoken overview
Read the transcript

Research with GCAM starts with knowing exactly what you are running. GCAM is a pipeline. Source data are processed by an R package called gcamdata into XML input files. A configuration file lists which input files to load, in which order, and the solver settings. The core model then solves one period at a time: it searches for the prices that make supply equal demand in every market, then moves five years on. It does not look ahead. Results go into a database, and you pull them out with queries, in R with rgcam or in Python with gcamreader. In the base year, share-weights are calibrated so that the model reproduces observed data; after that they are assumptions you choose and must report. One warning before anything else: the latest release is version 9.1, but the online documentation describes version 8.2, and transport units changed in between. Always write down the version, the input files, the configuration and the queries, so that anyone can rebuild your results.

The pipeline in one picture

GCAM is not one program but a chain of tools. Raw data (IEA energy balances, the UC Davis transport database, FAO land data, SSP population and GDP) is processed by gcamdata, an R package, into hundreds of input XML files. A configuration file lists which XML files to read and in what order. The C++ core reads them, solves every market in every period, and writes results to a BaseX output database. You read the database with queries, from ModelInterface, R (rgcam) or Python (gcamreader).

Why this matters

GCAM v9.1 was released on 2 June 2026, but its online documentation still describes v8.2. Between the two, the transport input files changed their units from million to billion passenger-km and from 1990 to 1975 dollars. A number copied from a v8.2 tutorial into a v9.1 add-on file can be wrong by a factor of 1,000, and GCAM will still run. Research with GCAM starts with knowing exactly which version, which file and which unit you are touching.

How GCAM solves: markets, not optimisation

Every period, GCAM looks for a set of prices at which supply equals demand in every market at once: crude oil, electricity in each region, land in each land unit, water in each basin, and constraint markets such as a CO2 cap. Write the excess demand of market m as a function of all prices p:

Fm(p) = Dm(p) − Sm(p) = 0    for every market m(3.1)

The solver works in log prices and scales each market's excess demand so that a market measured in EJ and one measured in km³ count equally. Its main engine is Broyden's method: a Newton-like step that reuses an approximate Jacobian instead of recomputing all derivatives each iteration. Bisection and a preconditioner bring starting guesses close enough for Broyden to converge. A typical regional run solves a few hundred markets.

Bk δx = −F(xk),   x = ln p,   then B is updated from the observed change in F(3.2)

The model is recursive-dynamic: each period is solved with the information of that period only, then the model steps forward five years. Nobody in GCAM knows a carbon price is coming; plants built in 2030 stay until they retire even if a policy arrives in 2035. This is the main contrast with intertemporal optimisation models such as MESSAGEix (Go 2, module 2.8).

Was the run solved? Read the log

A finished GCAM run is not the same as a solved one. Each period's solution is written to exe/logs/main_log.txt; a run that completes ends with "Model exiting successfully". If a period fails to reach the tolerance within max-model-calcs, the solver reports it and the model continues from an unsolved state. Results from an unsolved period look like any other numbers in the database.

Worked calculation

One market, by hand, the way Broyden would

  1. Excess demand F(p) = 1000 − 4p − 6p. Guess p0 = 80: F = 1000 − 800 = 200.
  2. Second guess p1 = 90: F = 1000 − 900 = 100.
  3. Secant slope B = (100 − 200) ÷ (90 − 80) = −10.
  4. Step δp = −F ÷ B = −100 ÷ −10 = 10, so p2 = 100.
  5. F(100) = 1000 − 1000 = 0: solved. In one dimension Broyden is the secant method; in many dimensions it updates a whole matrix of such slopes.

Answer: price 100, as in the week 4 toy market

Pitfall

"The run finished, so the scenario is valid." Unsolved periods, a constraint that is not binding (and so cannot be solved as a market), or an add-on file silently ignored because of a misspelt region name all produce a database. Every research run needs three checks: the log says each period solved; the base years reproduce calibration data; the variable you changed actually changed in the output (query it directly).

Calibration: what the share-weights are doing

In every base year GCAM must reproduce observed energy use by fuel, sector and region. It does this by solving for share-weights: the αi in the logit share equation (module 3.2). Whatever the costs say, the share-weight adjusts so that the base-year shares match the data. In the future, the share-weights are carried forward or moved along assumed paths (interpolation rules). This is powerful and dangerous: a share-weight silently absorbs everything the cost data miss, including infrastructure, preferences, regulation and data error.

Research note

Treat future share-weight paths as assumptions you must report, not as model output. In the current transport files, battery-electric car share-weights are 0 until the first future year and reach 1 by 2030 along an s-curve; in v5.4 they were 0.25 in 2030 and 0.625 in 2050 (A54.globaltranTech_shrwt_revised.csv). The same costs give very different electric-vehicle futures under the two paths. Module 3.6 shows how to test this.

Read transport results with gcamreaderPythonDownload
"""read_transport.py - pull the kit's transport queries from a GCAM output database (gcamreader),
or load the synthetic sample data, and save tidy CSVs for the other analysis scripts.

Usage
  python read_transport.py --sample                       # no GCAM needed (synthetic data)
  python read_transport.py --db /path/to/gcam/output --dbname database_basexdb
Needs for --db: pip install gcamreader (1.5.0, Python >= 3.11) and Java on the PATH.
API used (gcamreader README): LocalDBConn(dbpath, dbfile), parse_batch_query(file), conn.runQuery(q).
Filtering queries by q.title is an assumption about the Query object; if it fails, print dir(q).
The --db path has NOT been run against a real database; the --sample path is tested.
Output: analysis/out/{service_by_mode, energy_by_mode_fuel, co2_transport}.csv with columns
  scenario, region, [sector, mode, fuel], year, value, units
"""
import argparse, os
import pandas as pd

HERE = os.path.dirname(os.path.abspath(__file__))
QFILE = os.path.join(HERE, "..", "queries", "transport_queries.xml")
WANT = {"service_by_mode": "transport service output by mode",
        "energy_by_mode_fuel": "transport final energy by mode and fuel",
        "co2_transport": "CO2 emissions by sector (excluding resource production)"}
SAMPLE = {"service_by_mode": "transport_service_output_by_mode.csv",
          "energy_by_mode_fuel": "transport_final_energy_by_mode_and_fuel.csv",
          "co2_transport": "CO2_emissions_by_sector.csv"}


def tidy(df):
    df = df.rename(columns={"Year": "year", "Units": "units", "input": "fuel"})
    if "sector" in df and "mode" not in df:   # CO2 query: keep transport sectors only
        df = df[df["sector"].str.startswith("trn_")]
    return df


def from_db(db, dbname):
    import gcamreader
    conn = gcamreader.LocalDBConn(db, dbname)
    queries = gcamreader.parse_batch_query(QFILE)
    out = {}
    for key, title in WANT.items():
        q = [x for x in queries if getattr(x, "title", None) == title]
        if not q:
            raise SystemExit(f"query '{title}' not found in {QFILE}")
        out[key] = tidy(conn.runQuery(q[0]))
    return out


def from_sample():
    return {k: tidy(pd.read_csv(os.path.join(HERE, "sample_data", f))) for k, f in SAMPLE.items()}


def main():
    ap = argparse.ArgumentParser()
    g = ap.add_mutually_exclusive_group(required=True)
    g.add_argument("--sample", action="store_true")
    g.add_argument("--db")
    ap.add_argument("--dbname", default="database_basexdb")
    a = ap.parse_args()
    data = from_sample() if a.sample else from_db(a.db, a.dbname)
    os.makedirs(os.path.join(HERE, "out"), exist_ok=True)
    for k, df in data.items():
        p = os.path.join(HERE, "out", f"{k}.csv"); df.to_csv(p, index=False)
        print(f"{k:<22} {len(df):>5} rows, scenarios {sorted(df.scenario.unique())} -> {p}")


if __name__ == "__main__":
    main()

# read_transport.R - pull the kit's transport queries with rgcam, or load the synthetic sample data,
# and save tidy CSVs (same output as read_transport.py).
#
# Usage:  Rscript read_transport.R sample
#         Rscript read_transport.R db /path/to/gcam/output database_basexdb
# Needs for db: rgcam (remotes::install_github("JGCRI/rgcam")) and Java.
# rgcam API (rgcam vignette): localDBConn(dbPath, dbFile); addScenario(conn, proj, scenario, queryFile);
#   getQuery(proj, title). rgcam names the year column "year". The db path has NOT been run against
#   a real database; the sample path is tested.
suppressMessages({library(dplyr); library(readr)})
args <- commandArgs(trailingOnly = TRUE); mode <- if (length(args)) args[1] else "sample"
here <- tryCatch(dirname(normalizePath(sub("--file=", "", grep("--file=", commandArgs(), value = TRUE)))), error = function(e) ".")
qfile <- file.path(here, "..", "queries", "transport_queries.xml")
want <- c(service_by_mode = "transport service output by mode",
          energy_by_mode_fuel = "transport final energy by mode and fuel",
          co2_transport = "CO2 emissions by sector (excluding resource production)")
sample_files <- c(service_by_mode = "transport_service_output_by_mode.csv",
                  energy_by_mode_fuel = "transport_final_energy_by_mode_and_fuel.csv",
                  co2_transport = "CO2_emissions_by_sector.csv")
tidy <- function(df) {
  df <- rename_with(df, ~ c(Year = "year", Units = "units", input = "fuel")[.x] %||% .x)
  if ("sector" %in% names(df) && !"mode" %in% names(df)) df <- filter(df, startsWith(sector, "trn_"))
  df
}
`%||%` <- function(a, b) ifelse(is.na(a), b, a)
if (mode == "sample") {
  data <- lapply(sample_files, function(f) tidy(read_csv(file.path(here, "sample_data", f), show_col_types = FALSE)))
} else {
  library(rgcam)
  conn <- localDBConn(args[2], ifelse(length(args) >= 3, args[3], "database_basexdb"))
  prj_file <- file.path(here, "out", "transport.dat"); dir.create(dirname(prj_file), showWarnings = FALSE)
  scen <- listScenariosInDB(conn)$name
  for (s in scen) prj <- addScenario(conn, prj_file, s, qfile)
  data <- lapply(want, function(t) tidy(getQuery(prj, t)))
}
dir.create(file.path(here, "out"), showWarnings = FALSE)
for (k in names(data)) {
  p <- file.path(here, "out", paste0(k, "_R.csv")); write_csv(data[[k]], p)
  cat(sprintf("%-22s %5d rows, %d scenarios -> %s\n", k, nrow(data[[k]]), length(unique(data[[k]]$scenario)), p))
}

Research notes

  • A GCAM result is the end of a chain: source data, gcamdata, input XML, configuration, solver, database, queries
  • GCAM is recursive-dynamic: it clears markets one 5-year period at a time, with no foresight
  • Share-weights reproduce the base year; after that they are your assumptions and must be reported
  • Record version, inputs, configuration and queries; the docs describe v8.2 while the release is 9.1
