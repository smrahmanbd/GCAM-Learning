Research brief

In this module you will

  • Write an add-on XML file that changes a technology's cost or a mode's load factor
  • Set a share-weight path with interpolation rules for a new technology
  • Implement a carbon tax, an emissions constraint and a ZEV standard as a credit market
  • Run a scenario matrix with a batch file, and know when to change gcamdata instead
Spoken overview
Read the transcript

This is where your design becomes files. Each scenario is a small add-on XML file that repeats GCAM's own nesting, region, sector, subsector and technology, down to the value you want to change, and nothing else. Load it after the base files in the configuration, because later files win. Lever one is cost: for example, cut the non-fuel cost of battery electric cars by thirty percent from 2030. Lever two is share-weights: they decide when a new technology can enter, and interpolation rules decide how the path continues after the last year you set. Lever three is service: load factors and speeds. Lever four is policy. A carbon tax is a fixed price path. A net-zero target is an emissions constraint, and GCAM finds the price that meets it. A zero-emission vehicle standard can be built as a credit market that cars buy into and electric cars supply. Run all scenarios together with a batch file. And when a change must apply everywhere and consistently, make it in gcamdata instead of by hand. None of the course's XML templates has yet been run in a live GCAM installation, so test them first.

The anatomy of an add-on file

An add-on XML file repeats the path from <world> down to the object you want to change and sets only the values you change. GCAM reads files in the order the configuration lists them; when a later file names an object that already exists, it updates it rather than creating a new one. So an add-on must come after the core file that creates the object, and every name on the path (region, supplysector, tranSubsector, technology) must match exactly. A misspelt name does not cause an error: it quietly creates a new, empty object that nothing uses.

Why this matters

In GCAM's Middle East data, a petrol compact car costs about $0.286 per passenger-km in money and a battery car $0.328 (2020, our worked example). That 15 % gap gives battery cars only 23 % of the pair at the car exponent of −8. Cut the battery car's non-fuel cost by 30 % and the gap flips to -19 %, and its share jumps to 81 %. One number in one add-on file moves the whole story — which is why every number in that file needs a source.

In GCAM

Element names were checked against the C++ XML names in cvs/objects/ and the ModelInterface headers in input/gcamdata/inst/extdata/mi_headers/ModelInterface_headers.txt (gcam-core v9.1). The fastest way to get a correct path is to open the core file you are modifying, transportation_UCD_CORE.xml, find the object, and copy its parents.

Lever 1: costs

The non-fuel cost of a transport technology is its input-cost on the minicam-non-energy-input, in dollars per vehicle-km. GCAM divides it by the load factor to get dollars per passenger-km (Eq. 3.3). Fuel enters through a minicam-energy-input with a coefficient (energy per vehicle-km) whose price GCAM finds in the fuel market.

Worked calculation

What a 30 % cut in BEV non-fuel cost does (Middle East compact car, 2020 values, illustrative fuel prices)

  1. Non-fuel cost per vkm: 0.741 → 0.741 × 0.7 = 0.518 $/vkm.
  2. Add fuel 0.0257 $/vkm, divide by load factor 2.33: (0.518 + 0.0257) ÷ 2.33 = 0.233 $/pkm.
  3. Compare the petrol car at 0.286 $/pkm: BEV is now -18.5 % (it was +14.8 %).
  4. Absolute-cost logit (Eq. 3.6), exponent −8, p0 = ICE cost as in Figure 3.4: BEV share of the pair 23 % → 81 %.

Answer: BEV share 23 % → 81 % of the two-car choice (money cost only; time cost is the same for both)

Pitfall

Units changed in v8.5. Transport non-fuel costs moved from 1990$ to 1975$ per vkm and intensities from BTU per vkm to EJ per billion vkm; service is in billion pkm/tkm. A 1990$ value must be multiplied by about 0.47 (gcamdata's gdp_deflator(1975, 1990) = 27.80 ÷ 59.31, from the BEA deflator series in R/pipeline-helpers.R) before it goes into a v9.1 add-on. Copying a v8.2 tutorial value unchanged makes the car about twice as expensive, and the model will still solve.

Lever 2: share-weights and their interpolation rules

Share-weights (module 3.1) are where calibration lives, so they are also where hidden assumptions live. Future share-weights for transport technologies are set globally in the global-technology-database and moved between years by interpolation rules. If you set a share-weight for 2025 but leave the default rule in place, the rule will re-impose its own path for later years. To make your value stick, add an interpolation-rule with a fixed function (or a path you choose) in the same file.

Research note

Report share-weights as a scenario dimension. In the current files the BEV share-weight reaches 1 by 2030 on an s-curve; in v5.4 it was 0.25 in 2030 and 0.625 in 2050. A study that sets BEV share-weights to 1 from 2025 (as some US studies do) is answering "what if consumers treated BEVs like petrol cars from now on?" — a legitimate question, but not a forecast and not a policy. In module 3.6's tornado chart the share-weight path is the second-largest influence, after cost.

Lever 3: how much service, at what speed

Three mode-level levers change how people travel rather than what they drive. The load factor (passengers per vehicle) divides every per-vehicle cost and intensity; the speed of a mode sets its time cost; the income and price elasticities of trn_pass set how much travel there is at all (module 3.2).

Worked calculation

Fewer people per car: the load factor falls from 2.33 (2020) to 2.0 (the UC Davis 2050 value, petrol compact car)

  1. Money cost per vkm = non-fuel 0.635 + fuel 0.0332 = 0.668 $/vkm.
  2. At 2.33 passengers: 0.668 ÷ 2.33 = 0.286 $/pkm.
  3. At 2.0 passengers: 0.668 ÷ 2.0 = 0.334 $/pkm, +17 %.
  4. Energy and CO2 per pkm rise by the same 17 %, because intensity is also per vehicle-km.

Answer: +17 % on cost, energy and CO₂ per passenger-km

In GCAM

Input element <loadFactor>; output database name load-factor (reporting/source/xml_db_outputter.cpp), which is what the query "transport load factors" reads. Mode-level levers sit on tranSubsector: <share-weight year=…>, <speed year=…>, <time-value-multiplier year=…>. Demand elasticities sit on <energy-final-demand name="trn_pass"> as <income-elasticity year=…> and <price-elasticity year=…>.

Lever 4: policies

GCAM has three policy objects that cover almost every transport policy question. Module 3.4 explained when to use which; here is how each looks.

A carbon price

An emissions constraint (net zero)

With <constraint year=…> instead of fixedTax, GCAM treats the emissions cap as a market and solves for the price that clears it (the shadow price). Linked gases enter through <linked-ghg-policy> with price-adjust (global-warming potential) and demand-adjust; setting demand-adjust to 0 for CO2_LUC restricts the cap to fossil and industrial CO2, as the core file global_ffict.xml does.

A ZEV standard as a credit market

A mandate such as "30 % of car passenger-km must be zero-emission" becomes a market for credits. Every car technology demands 0.3 credits per unit of output; BEVs and FCEVs supply 1 credit per unit; a policy-portfolio-standard of type RES makes demand equal supply. GCAM finds the credit price that does it: a tax on petrol cars and a subsidy to zero-emission cars at the same time. Note the share is in passenger-km, not vehicle sales, because GCAM has no vehicle counts.

Worked calculation

Units of a carbon price in GCAM

  1. Policy files declare <price-unit>1990$/tC</price-unit>: dollars of 1990 per tonne of carbon.
  2. One tonne of carbon is 44 ÷ 12 = 3.667 tonnes of CO2.
  3. So $100 per tonne CO2 (in 1990$) = 100 × 3.667 = $367 per tonne C.
  4. Convert today's dollars to 1990$ with the GDP deflator first; say which year's dollars your paper reports.

Answer: $100/tCO₂ = $367/tC (both in 1990$)

Worked calculation

Balance of a 30 % ZEV credit market

  1. Credit demand = 0.3 × (all car pkm). Credit supply = 1 × (ZEV car pkm).
  2. Market clears when 1 × ZEV pkm = 0.3 × all pkm, so ZEV pkm ÷ all pkm = 0.3.
  3. If ZEVs already exceed 30 % without the policy, supply exceeds demand: the credit price falls to zero (the constraint does not bind).
  4. If they fall short, the credit price rises until enough cars switch — that price is the policy's marginal cost per credit.

Answer: the credit price is the cost of the last unit of compliance

Research note

Not yet verified in a running model: (1) whether a transport-only carbon price can be set by renaming the CO2 object on transport technologies (CO2_TRN); (2) whether negative output-ratio values are accepted for an intensity-style standard; (3) a sustainable-aviation-fuel mandate, which needs an aviation-specific liquids pass-through sector because aviation draws on the generic refined liquids enduse. Test each on one region and one period before building a study on it.

Batch runs: the scenario matrix as a file

GCAM's batch mode runs every combination of the component sets listed in a batch file. Each ComponentSet is one dimension (for example "BEV cost" with Reference and Low); each FileSet inside it is one level and lists the add-on files for it. Point BatchFileName in the configuration to the batch file and set BatchMode to 1.

Systematic changes: go through gcamdata

For changes to many regions or years, edit the source tables and rebuild the XML rather than writing long add-ons. Remember that OTAQ_trn_data_EMF37.csv overrides the UC Davis table for most vehicle costs and intensities, so editing UCD_trn_data_CORE.csv alone may change nothing. For a clean record of your change, write a user-modification chunk and pass it to the driver:

Pattern from input/gcamdata/vignettes/usermod_vignette.Rmd and R/driver.R (gcam-core v9.1). Check how the year column is named after reading ("2030" vs X2030) in your version.

Pitfall

"My add-on changed nothing." The usual causes, in order: (1) the file is listed before the core transport file; (2) a name on the path is misspelt or uses a v8.2 name (hydrogen fuels were renamed in v8.8 to H2 LDV, H2 MHDV, LH2); (3) an interpolation rule overwrote your share-weight; (4) the value is in the old units and so is a factor of 1,000 off in the other direction. Always query the variable you changed.

Try it

  1. Write the XML path (just the element names and attributes) that sets the speed of Passenger Rail in the Middle East to 60 km/h in 2040.
  2. A v8.2 paper reports a BEV non-fuel cost of 0.30 1990$/vkm. What value goes into a v9.1 add-on? (Use the deflator ratio above.)
  3. Design a ZEV credit market for trucks only. Which technologies demand credits, which supply them, and what is the coefficient for a 20 % standard?

Research notes

  • An add-on repeats GCAM's nesting down to the one value it changes, and loads after the base files
  • Match units to your release: billion pkm and 1975$ in transport since v8.5
  • Share-weights with interpolation rules control when new technologies can enter
  • A carbon tax fixes the price; a constraint fixes emissions; a ZEV standard can be a credit market
  • Make systematic, everywhere changes in gcamdata, not by hand

Check yourself

1. An add-on file must contain…

It repeats the path (region, sector, subsector, technology, period) to the changed values only.

2. A carbon tax of $100 per tonne of CO2 is about how much per tonne of carbon?

Multiply by 44/12 ≈ 3.67.

3. In a ZEV credit market, who supplies credits?

ZEVs produce credits; other cars must buy them, so the credit price penalises them.

4. When should you change gcamdata instead of writing an add-on?

Systematic changes are safer in the data system, rebuilt from source.
